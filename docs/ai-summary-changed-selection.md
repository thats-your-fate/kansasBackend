# New or changed AI summary selection

The AI summaries page now opens the **Changed wells** tab, which includes both new wells and existing summaries whose facts changed. Use **Run new or changed wells** for the manual weekly refresh. The **All eligible wells** tab is the explicit force-regeneration option. New wells use the existing activity-date eligibility rules. Previously summarised wells are also rechecked even if their last qualifying activity was removed; current public identity, privacy and site-specific spud restrictions still apply. This does not expand public source-fact scope.

The planner reads the current public inference facts and compares them with the latest saved input for the selected model and current prompt version. New wells, corrections, amended production and removed facts are selected. Identical input is excluded before applying the generation limit, so unchanged wells cannot hide older changed wells. A different model or prompt version has a separate baseline and may select all eligible wells. Rejected summaries with identical facts are left alone unless the All eligible wells tab is selected.

PostgreSQL sites plan in the background by snapshotting only candidate identities once, then checking facts in groups of 250 with sequential reads on the existing bounded worker pool. The expensive eligibility aggregation is not repeated per group. The log reports selection progress; only selected items enter the inference queue. Count wells now starts a separate exact comparison scan and reports progress before showing the full new/changed/unchanged totals. The worker rechecks the saved input before inference, including on resume. Stored JSON comparison avoids false changes from object-key order; Pennsylvania retains its source-provenance comparison so a changed source cannot bypass its existing publication freshness checks. Texas plans in a native background worker, with a read snapshot per well and no write transaction held across the scan; it checks exact public facts before applying its limit.

No schema migration or new runtime dependency is needed. The existing publication/review policy, credentials and inference endpoint configuration are retained. No recurring timer is installed or enabled by this change: a caller can use the normal authenticated run endpoint with the force flag false; the disposable inference token remains in worker memory. The owner chose a manual run about once a week; no automatic schedule is part of this release.

Deploy only after tests and review, from exact pushed Git commits through the site's approved native workflow. Preparing or committing this change is not a deployment receipt.

## Exact count preview

The **Count new / changed** button scans the same candidate identities and exact saved-input comparison as generation, without a generation cap. The persistent result panel reports new wells, changed existing summaries and unchanged inputs, and separately shows how many fit within the current run limit. Counting never changes that limit, needs no GPU endpoint/token, and never creates runs, queue items or summary revisions. No inference request is made.

The scan runs in the background with progress, one active scan per API process. Repeated requests for identical filters share that active scan; a fresh click after completion starts a fresh scan. Model/date changes invalidate the browser's result and discard responses from its previous filters. Partial or failed scans are never labelled exact; an empty completed scan correctly reports zero. Results carry their completion time, and generation still rechecks facts because source data can change after counting. Restarting the API clears the in-memory preview; count again afterward.

PostgreSQL counting uses the existing generation planner's preview mode and one additional read-only connection, with bounded statement/lock timeouts and no inventory-wide transaction. Preview mode cannot log or enqueue; the database also enforces read-only operation. Texas uses the same eligibility SQL and saved-input comparison, snapshots only identities to a file-backed temporary table, and reads each well in its own snapshot on a connection opened read-only for the main database. Counting stops after a read failure rather than presenting partial results as a total. No migration, recurring job, runtime dependency, source-adapter or publication-policy change is part of counting.
