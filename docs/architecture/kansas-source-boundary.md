# Kansas Source Boundary and Module Architecture

**Task:** KS-001, KS-002, KS-003
**Status:** Scaffold, source configuration, and Kansas-specific modeling decisions complete. Health-check API + CLI skeleton only, no ingestion code.
**Scope:** Establishes what Kansas reuses from the pattern common to every sibling Future Wells state backend, what is explicitly out of scope until a later task, and the proposed module tree. Canonical data contracts live in `future_wells_kansas_backend_marketing_codex_tasks.md` §6 and are authoritative; this document does not redefine them.

---

## 1. Two-agency source model

Kansas has no single WOGCC/OCC-equivalent regulator. Two agencies split the role every other sibling state backend gets from one:

- **Kansas Geological Survey (KGS)** — the statewide well and production foundation: well master, leases/production, fields, well documents (jointly with KCC). Nightly/monthly cadence, research-oriented, generally the more stable/less time-sensitive layer.
- **Kansas Corporation Commission (KCC)** — the regulatory signal: operators, drilling intents, approved transfers, conservation dockets. Continuously updated or rolling-window, time-sensitive, and the layer with real legal-use restrictions (no commercial solicitation from operator/contact data).

Every `SourceDescriptor` in `src/constants.rs::SOURCES` is tagged `KgsFoundation`, `KccRegulatory`, or `Documents` accordingly. Code and docs should say "KGS" or "KCC" explicitly rather than inventing a combined acronym — the two are legally and operationally distinct data owners.

## 2. Fixed architecture decisions (KS-001)

1. **Envelope.** Every successful API response is `{data, meta}` (`src/api/envelope.rs`), matching the convention Wyoming introduced and every state backend since has followed. `Meta.production_through` exists specifically so the site never implies KGS production coverage is current through the present month — display it as source-coverage metadata, per the plan's explicit instruction.
2. **Raw-first ingestion (once KS-004 lands).** Every parser must write an immutable raw-row table before any normalization/materialization step — nothing from KGS or KCC gets reinterpreted at parse time and silently discarded.
3. **Rolling-window sources must be snapshotted daily.** Drilling intents (365-day KCC window) and approved transfers (90-day KCC window) disappear from the source once the window rolls — KS-007/KS-008 must run daily and persist history in Kansas's own tables, never rely on the source remaining queryable for a past date.
4. **No commercial-solicitation surface.** Operator/contact addresses, phone numbers, and named individuals from KCC's operator search must never be exposed through the public API or indexed by the marketing site. This is a legal restriction from KCC, not a style preference — do not add an "operator contact" field to any public-facing contract.
5. **Metadata-first documents.** KS-011 (documents) starts by cataloguing document *metadata* (type, date, well/lease link, source URL) — never scrapes or mirrors document bytes behind a login, and never attempts to bypass a "confidential/restricted" marker on a KGS or KCC record.
6. **KCC-Connect, not legacy eStar, for new docket filings.** KCC moved post-November-2025 conservation-docket filings to KCC-Connect; KS-012 (dockets) must be built against KCC-Connect, with eStar consulted only for historical dockets predating the migration if that's ever in scope.
7. **Advisory-lock ingestion guard.** Every ingestion command in `ks_ingest` that writes must take a Postgres advisory lock so two overlapping runs (a manual run + a cron-triggered `sync-current`) cannot race.
8. **CLI dispatch via `clap`**, matching the newer sibling-state convention (not hand-rolled arg parsing).
9. **Bootstrap from a clean template, not a forked sibling repo.** Every state backend that was forked from another state's repo (ND from OK, NM from OK) has shipped silent state-identity bugs (literal `DEFAULT 'OK'` leftovers). Kansas's migrations and code are authored fresh against this project's own contracts.

### Kansas-specific modeling decisions (KS-003)

Full rationale lives in the task doc §3; the fixed rules are:

10. **API number is canonical identity; KGS KID and KCC permit number are aliases**, stored in a dedicated `ks_well_source_alias` table, never as the well's primary key — KGS itself documents the KID as not necessarily permanent (task doc §3.1).
11. **Operator relationships are versioned, append-only rows** (`ks_well_operator_history`: `valid_from`/`valid_to`/`source`/`match_method`/`confidence`/`is_current_reported`), never a field overwritten because a fuzzy lease-name match suggested a transfer (task doc §3.2).
12. **Source coordinates are preserved alongside a derived display geometry.** `source_latitude`/`source_longitude`/`source_crs` (KGS's NAD27-or-GPS-mixed values) are never discarded; `display_geometry_4326` is an additive transform, requested as `outSR=4326` from the ArcGIS adapter (task doc §3.3).
13. **Production stays lease-level; sentinel months are classified, not blended.** No even split of lease production across wells; month `0` (yearly total) and month `-1` (starting cumulative) are tagged `ProductionRecordKind::YearlyTotal`/`StartingCumulative` and excluded from the default monthly series (task doc §3.4, `constants::classify_production_month`).
14. **Lifecycle is derived from `WELL_CLASS`+`STATUS`+`STATUS2` together, with all three preserved raw.** `constants::WellLifecycleStatus::Unknown` for an unmapped combination must surface in a QA report, never silently collapse to `Inactive` (task doc §3.5).
15. **Horizontal/directional is a badge, not a geometry claim.** `horizontal_or_directional` follows the API's directional indicator; `trajectory_available` stays `false` for every well at launch — never draw a guessed lateral from a surface point (task doc §3.6).
16. **Two hard data-use controls are code, not documentation**, already implemented and tested: `constants::MIN_PRODUCTION_YEAR = 1990` (blocks re-ingesting IHS-licensed pre-1987 production; `KGS_PRODUCTION_FILES` already only lists 1990+ archives, guarded by a test) and `privacy::assert_no_forbidden_fields` (blocks personal/contact fields from any public response; every operator/intent/transfer response type's test suite must call it) (task doc §3.7).

### Shared-platform correction (task doc §10, recorded 2026-09-05)

17. **No Kansas-specific admin/auth system.** No `users`/`sessions` table, no argon2 login, no `admin_auth` migration. A read-only investigation found Colorado and Wyoming each independently built exactly this for internal ingestion review — the same thing twice — when `futureBackend` already provides it generically (`AuthenticatedAdmin` + `routes/admin_import_status.rs`, keyed by jurisdiction). Kansas's ops review goes through that once KS-020 registers Kansas as a jurisdiction.
18. **KS-020 (`state-export-v1` export) is load-bearing, not optional.** `kansasMarketing` deliberately never builds public search/map/browse (item 19), so the shared `futurewells.co/user-area` — fed by this export — is the only way Kansas wells ever reach a real search/map/save experience. Target `futureBackend/src/imports/contracts/v1/mod.rs` exactly; populate `SourceEnvelopeV1.source_payload` with the complete raw record for full lineage.
19. **`kansasMarketing` carries no public well search, map, or browse-first navigation.** It is a regional SEO/lead-gen content site; every entity-adjacent page converts to the shared `user-area` via the ported `RecordConversionCta` component rather than offering its own directory/search/map.
20. **Every task from KS-004 onward ships as one focused PR** with tests, real fixtures, migration notes, rollback notes, and an operational runbook update (`docs/ops/*.md`) — a standing delivery requirement, not a one-time task.

### KS-03: the KGS well snapshot importer (recorded 2026-09-05)

21. **ArcGIS object-ID listing truncates below the layer's real row count**, confirmed live: `returnIdsOnly` caps at 100,000 of the real 519,092-row total and reports `exceededTransferLimit: true` rather than surfacing it via `maxRecordCount` (which governs feature-fetch batch size, a separate limit). `resultOffset` pagination does not fix this — only `WHERE OBJECTID > :after ORDER BY OBJECTID` cursor pagination does. Any future ArcGIS-backed importer (fields, leases) must assume the same undocumented truncation and use the same cursor pattern, not trust `maxRecordCount` alone.
22. **ArcGIS and ZIP are different schemas, not the same data in two containers.** Field names, date formats, and even field *presence* differ (the ZIP has no `WELL_CLASS` and no `COUNTY`) — `ks_well_raw_snapshot.raw_data` stores each source's native shape verbatim, tagged by `source_format`; KS-04's normalizer must branch on it, never assume a unified raw shape.
23. **A rectangular Kansas bounding box, not a precise state polygon, backs the geometry half of membership classification** — a deliberate scope decision (`constants::KS_BOUNDING_BOX_*`), not an oversight. Paired with the county-name check, it keeps false positives low without a shapefile dependency; revisit only if border false-positives prove material in practice.
24. **Excluded (non-Kansas) records are retained, never dropped**, in `ks_well_raw_snapshot` with `kansas_membership_status = 'excluded_other_state'` and a reason — raw-first ingestion applies to excluded rows exactly as it does to included ones.
25. **A `completed` `ks_ingestion_run` is the only thing a materializer may ever read from.** KS-04 must filter `ks_well_raw_snapshot` by `ingestion_run_id` values whose run status is `completed` — never `running`, `failed`, or `rejected` — this is what "atomically publish only after QA passes" means in practice, since rows are staged incrementally during `running` but only become "real" once the run's QA gates (missing-object-ID check, source-change check, count-tolerance check) all pass.

### KS-04: normalize/materialize Kansas wells (recorded 2026-09-05)

26. **Lifecycle status is derived by ranking patterns globally across all three raw fields, never by exhausting one field before checking the next.** An earlier per-field-priority design (check STATUS2 fully, then WELL_CLASS, then STATUS) produced a real bug: a generic "Plugged and Abandoned" in STATUS2 masked a more specific "SWD" signal sitting in STATUS. Combine the fields, then match patterns most-specific-first.
27. **`display_geometry_4326` is only ever built from `'arcgis'`-sourced rows.** Only those were actually reprojected via `outSR=4326` at extraction time (KS-03); `'zip'`-sourced rows' coordinates are NAD27 (confirmed authoritative by reading `kgs.ku.edu/PRS/file_format.html` in full at KS-04), and get a `location_warning` instead of a fabricated display geometry. This is also why KS-03's staging columns were renamed from `geometry_wgs84_x/y` to `geometry_source_x/y` — the old name was factually wrong for the ZIP path.
28. **`horizontal_or_directional` and `trajectory_available` are hardcoded `false` for every well at KS-04**, not derived. The "directional indicator in the API" the original plan (§3.6) refers to was never confirmed against the real 53-field ArcGIS schema captured during KS-03's discovery — this is an open research item, not a silently-wrong guess.
29. **Materializer tests that exercise the tombstone rule must use `#[serial]`, listed *before* `#[tokio::test]`.** The tombstone scan is (correctly) global across every `ks_well` row sharing `source_format` — in production that's required correctness, but it means concurrently-running test functions against a shared test database mutate each other's wells for real. Confirmed empirically: `#[tokio::test]` then `#[serial]` compiles but does not actually serialize; the reverse order does.

### KS-05: import/normalize KCC operator licenses (recorded 2026-09-05)

30. **`kcc.ks.gov` is confirmed unreachable from this development environment**, checked four separate times across two sessions by three independent methods (`curl`, `nslookup`, `WebFetch`) — always DNS `ENOTFOUND`/`SERVFAIL`. Unlike KS-03/KS-04, KS-05 is built and tested only against a hand-built fixture page/CSV modeled on KCC's documented conventions ("active-only and all-operator downloads"), never the real service. Every format assumption below is unverified and flagged as such in code comments; confirm against a real fetch before production use — see `docs/ops/ks-05-kcc-operators-unverified.md`.
31. **Operator download links are discovered from the page's anchors at runtime (`source::kcc_html::discover_operator_links`), never a hardcoded filename** — matches an anchor whose combined visible-text+href contains "operator" plus a lifecycle keyword ("active" or "all"). Finding *neither* link is treated as a page-structure-change alert (the run is started and immediately `rejected` with the discovery error as its reason), never as "zero operators, successfully imported" — same discipline as KS-05's other "no silent zero" requirement below.
32. **A run with a discovered link but zero parsed operator records is rejected, not completed.** Distinct from decision 31 (link discovery itself failing): here the link resolves and downloads, but the CSV parses to zero rows — also treated as a likely format/schema change via `ingestion_run::reject_run`, never published as a legitimate empty result.
33. **CSV header matching is name-tolerant, not exact-string**, across several plausible header spellings per logical column (`parse::kcc_operators::csv_source`) — since the real header names have never been confirmed live, requiring one exact spelling would be brittle in a way that's indistinguishable from "the format actually changed." A genuinely missing license/name column still fails loudly (`CsvParseError::MissingLicenseColumn`/`MissingNameColumn`), it isn't silently guessed at.
34. **`ks_operator` has no street-address/phone/email/contact-person column at all** — not merely unselected by application code, structurally absent from the schema (migration `0008_ks_operator.sql`). Those fields, if present in a source row, exist only inside `ks_operator_raw_snapshot.raw_data`, which no public-facing code path may read. `source_city` is stored (KS-05 asked for it "only if already permitted by product policy") but is deliberately left out of `materialize::kcc_operators::PublicOperator` — no such policy decision has been made, so it stays out of every public payload until one is.
35. **Identity is always `kcc_license_number`, never a name match — `ks_operator_alias` is keyed off it, not off name similarity.** `normalize::kcc_operators::normalize_company_name` is deterministic (case/whitespace/trailing-punctuation only); it is never used to decide that two different license numbers are "the same operator." This is the structural version of KS-05's explicit "prevent aggressive mergers of similarly named companies."
36. **`active_status` is derived purely from which of the two documented lists a license appears on this run** (`normalize::kcc_operators::derive_active_status`), not from any status text a CSV might separately report: present on the active list → `active`; present only on the all list → `inactive`; present on neither (can't actually occur through the materializer, since a row only exists because it was staged from one of the two lists) → `unknown`. A license present on the active list but *not* the all list is a genuine data anomaly (the all list is documented as the complete roster) — surfaced via the active/all reconciliation counts, not hidden inside the status value.

### KS-06/KS-07: KCC drilling intents and approved transfers (recorded 2026-09-05)

37. **`ks_event` is Kansas-local, not a confirmed `futureBackend` shared event system.** The task-doc-level architecture instruction (§10) says to reuse shared components where they exist, the same way KS-02 reused `jurisdictions`/`data_sources` rather than inventing Kansas-local equivalents — but investigating whether `futureBackend` already has an event system was not possible in this session (no access to that checkout). `ks_event` (migration `0014_ks_event.sql`) is deliberately Kansas-local for now, mirroring the KS-02 precedent of keeping something internal when the shared equivalent can't be confirmed. Revisit and migrate into `futureBackend`'s event system if one is confirmed to exist.
38. **A plain `UNIQUE` constraint is not sufficient for idempotent daily import when the identity columns can be `NULL`.** A real bug, found and fixed during KS-07's own testing: `ks_operator_transfer`'s natural identity (`past_operator_license`, `new_operator_license`, `effective_date`, `lease_or_well_label`, `county`) initially used a plain `UNIQUE` constraint; Postgres treats `NULL` as distinct from `NULL`, so a transfer missing even one of those fields (a real possibility in KCC data) never conflicted on re-ingestion and silently duplicated on every run instead of upserting. Fixed by wrapping every column in `COALESCE(..., '<sentinel>')` inside a unique *index* rather than a table constraint, with `materialize::kcc_transfers`'s `INSERT ... ON CONFLICT` using the exact same expressions as the conflict target (Postgres requires syntactic, not just semantic, expression matching for `ON CONFLICT` to resolve to an expression index). Any future table using a multi-column natural identity where some columns may legitimately be absent should use this pattern from the start, not discover the gap via a flaky-looking idempotency test the way this one was found.
39. **Well-linking is a shared module (`materialize::well_linking`), not duplicated per importer.** KS-06 and KS-07 specify different-looking but structurally identical layered strategies (exact identifier → exact PLSS/name/license combinations → fuzzy candidate → unresolved) — the actual SQL lives in one place, and every "exact" lookup returns `None` (never a guess) when more than one row matches, which matters most for PLSS-only matching: a full section commonly contains many wells in real Kansas data, so that tier is expected to resolve rarely on its own.
40. **Fuzzy lease-name candidates are generated only when every exact tier has already failed, and are structurally incapable of overwriting a well's current operator** — there is no code path anywhere in this repository that reads a `fuzzy_candidate`-tagged link and writes to `ks_well` or any operator-history table (`ks_well_operator_history` doesn't exist yet; that join is KS-08). This is KS-07's "must not directly overwrite" requirement satisfied by absence of a write path, not by a runtime check that could be bypassed.
41. **Neither KS-06 nor KS-07's task-doc field list includes an explicit per-record source identifier** (no intent/permit number column for intents, no transfer-ID column for transfers) — both importers therefore treat a different field as the natural identity: `source_filename` for intents (assumed to be a per-record document filename), and the combination of operator licenses + effective date + lease label + county for transfers (since "source file" there reads as the shared daily results page, not a per-record filename). Both assumptions are unverified — see items 30/37 and the two new unverified-service docs below.
42. **`kcc.ks.gov` remains unreachable from this development environment for KS-06/KS-07 as well** — re-confirmed at the start of this task by the same three methods as KS-05 (`curl`, `nslookup`, `WebFetch`), all `SERVFAIL`/`ENOTFOUND`. Both importers parse an assumed HTML results table (`source::html_table::parse_first_table`) rather than a confirmed CSV download, since both source pages are documented as "search"/"search results" pages rather than KS-05's confirmed download links. See `docs/ops/ks-06-kcc-intents-unverified.md` and `docs/ops/ks-07-kcc-transfers-unverified.md`.

### KS-08: import Kansas fields and field geometry (recorded 2026-09-05)

43. **KGS is confirmed reachable — this importer was verified live, the same confidence level as KS-03/KS-04, not the "unverified" tier of KS-05/06/07.** Real discovery before any code: resolved the field ArcGIS item (`390ee1b9eade40bca42ee3534a813b20`) via the sharing API, confirmed its real 28-field schema and 8,089-feature count, downloaded and inspected all six active-field `.xlsx` files plus the abandoned-field `.xlsx` file directly. A real live run (`--limit-object-ids 20`) then materialized 8,078 real `ks_field` rows from real KGS data — see `docs/ops/ks-08-kgs-fields-live-smoke.md`.
44. **`f=geojson` is used instead of ArcGIS's native `{"rings": [...]}` geometry format for polygon layers**, confirmed live to work correctly against this service including `outSR=4326` reprojection. This offloads the outer-ring/hole-separation algorithm to the ArcGIS server itself (`source::arcgis::fetch_features_batch_geojson`) rather than reimplementing esri's ring-winding convention in Rust — a real, deliberate difference from KS-03's wells importer (which uses native esri point geometry via `fetch_features_batch`, since points have no ring structure to get wrong).
45. **A multi-part field (the same `FIELD_NAME` appearing as 2+ separate ArcGIS polygon features) is a real, confirmed-live phenomenon** (e.g. `FOREST CITY COAL GAS AREA`, `LEIKER EAST`), not a hypothetical edge case — `materialize::kgs_fields` collects every part sharing a field's identity into one `MultiPolygon` via `ST_Multi(ST_Collect(...))` rather than assuming one row per `FIELD_NAME`.
46. **Identity/matching across the three source components (ArcGIS, six active-file `.xlsx`, one abandoned-file `.xlsx`) is exact-name-only, via `normalize::kgs_fields::normalize_field_name`'s case/whitespace-only normalization — never fuzzy.** Confirmed live that the abandoned/active `.xlsx` files carry no `FIELD_KID` at all, so exact `FIELD_NAME` matching (case/whitespace-normalized) is the *only* way to join them to an ArcGIS-identified field; this is also the direct enforcement of the task doc's "do not merge two official field names merely because punctuation or directional words look similar."
47. **ArcGIS is authoritative for `active_status`; a field seen only in the `.xlsx` enrichment files (never in ArcGIS) is `unknown`, not guessed.** The abandoned-file's own existence is treated as a real (if secondary) signal — a field seen *only* in the abandoned file, never in ArcGIS at all, is marked `abandoned` rather than `unknown`, since that file's entire purpose is listing abandoned fields — but this is explicitly a fallback, never overriding a real ArcGIS `STATUS` value.
48. **Geometry validity is checked (`ST_IsValid`/`ST_IsValidReason`) and flagged, never silently repaired.** Confirmed live: KGS's own `Chase-Silica` and `Lost Springs` field polygons have real self-intersecting rings in the live ArcGIS data — a genuine KGS data-quality issue, not an artifact of this importer. `ST_MakeValid` was deliberately not applied automatically, since that would silently alter KGS's own reported boundary; the invalid geometry is stored as-is alongside `geometry_is_valid = false` and the exact self-intersection point from `ST_IsValidReason`.
49. **A real scaling characteristic, not a bug, was found during the live materialize run**: with ~8,000 distinct fields, each requiring several sequential `await`ed round-trips (upsert + alias + one insert per year of annual production), a full materialize run took several minutes. Correctness was verified at every step; a future optimization pass should batch the per-year production inserts rather than one `INSERT` per `(field, year)` pair — not done in this task since throughput wasn't part of the acceptance criteria, but recorded here so it isn't rediscovered from scratch. See `docs/ops/ks-08-kgs-fields-live-smoke.md`.
50. **`fetch_all_object_ids` was promoted from `parse::kgs_wells` (KS-03) into `source::arcgis` as a shared function** once KS-08 needed the identical cursor-pagination behavior — the same refactor discipline as KS-06/07's shared `well_linking` module: a second real caller is what justifies promoting something to shared, not a hypothetical future one.
51. **The well-operator-history numbering guess from KS-06/KS-07 (items 40-41, and multiple task-doc references) was wrong.** Those entries speculated the next authoritative task after KS-07 would be numbered "KS-08" — the user has since assigned KS-08 to this field-import task and KS-09 to the lease dimension instead. `ks_well_operator_history` has no assigned task number as of this recording; every earlier "KS-08" reference to it (task doc §6.1b and its reconciliation-table rows) has been corrected to say "not yet assigned" rather than silently left wrong.

### KS-09: Kansas lease dimension and well-to-lease relationships (recorded 2026-09-05)

52. **The task doc's requested "field" association does not exist in the real all-leases file** — confirmed by downloading and inspecting `all_kansas_leases.txt` directly: its real header has no `FIELD` column at all. `ks_lease.field_name` exists as a real, honestly-nullable column rather than being silently dropped from the schema; it stays `NULL` until a different source actually populates it. This is the same "flag the gap, don't paper over it" discipline as KS-06's missing intent-identifier column.
53. **`KGS_LEASE_FORMAT`'s documented page describes a different file's columns than the file this task actually imports.** The format page (fetched live) documents `PRODUCT`/`WELLS`/`MONTH-YEAR`/`FIELD` — the monthly *production* file's shape — while the real `all_kansas_leases.zip` (also fetched and inspected live) has a materially different header (`LEASE_KID`, `LEASE`, `DOR_CODE`, `API_NUMBER`, `PRODUCES`, `PRODUCTION`, `YEAR_START`, `YEAR_STOP`, no `FIELD`). A documented format page is not proof of a specific file's shape — the real downloaded file's own header row is what this importer trusts.
54. **`PRODUCES` is sometimes the literal string `"NULL"`** (2,359 of 98,639 real rows, confirmed by direct inspection), not a blank/missing value — `normalize::kgs_leases::derive_product` treats it as its own explicit case (`LeaseProduct::Unknown`), never conflated with a genuine parse failure.
55. **A lease's own `API_NUMBER` field can list more than one API number**, comma-separated — confirmed live and real (e.g. one lease record spanning several wells). This is the mechanism behind the task doc's "API numbers listed in production data" well-linking tier; `normalize::kgs_leases::parse_api_number_list`/`normalize_api_token` split and normalize each token independently, never fuzzy-matched.
56. **Oil and gas identifiers are matched in product-scoped queries, never a shared lookup** — `materialize::kgs_leases::find_wells_by_exact_identifier` selects the well's `oil_kid`/`oil_dor_id` columns only for an oil-product lease and `gas_kid`/`gas_dor_id` only for a gas-product lease, so a coincidentally-identical numeric value used as both an oil lease's KID and an unrelated well's gas KID can never cross-link (task doc: "oil and gas identifiers do not collide"), tested directly with a deliberate same-value fixture.
57. **Well-to-lease linking follows a different matching shape than KS-06/07's well-linking**: a lease legitimately covers *multiple* wells, so `find_wells_by_exact_identifier` and the API-number tier return every matching well rather than requiring exactly one match (contrast `materialize::well_linking`'s single-target tiers, built for identifying *one* well from an intent/transfer). The name-match tier is a last resort only when neither exact tier found any well at all — direct enforcement of "exact ID-based links take precedence over name matching."
58. **"Unresolved production APIs are reported" reuses the existing generic `ks_source_rejection` mechanism** (`ingestion_run::record_rejection`) rather than a new table — the same reuse-before-inventing discipline KS-05 already applied when it reused `reject_run` for "zero operators."
59. **A real scaling characteristic, worse than KS-08's, was found and not fixed in this task**: materializing 200 real leases (a small sample, not the full 98,639-row archive) took several seconds under the same sequential-round-trip pattern as KS-08's fields. Extrapolated to the full archive, a real production run would take on the order of hours. This task deliberately verified correctness against a 200-row real sample plus the full fixture suite rather than attempting a full-scale live materialize — see `docs/ops/ks-09-kgs-leases-live-smoke.md`. The batch-insert optimization recommended for KS-08 (item 49) applies here more urgently.
60. **A real cross-test-file fixture collision was found and fixed during this task's own testing**: `tests/kgs_leases_materialize.rs`'s "unresolved API" test used the placeholder API number `15-009-99999`, which — coincidentally — is the exact same fake API-14 value (`15009999990000`) already used as a well fixture in `tests/kcc_intents_materialize.rs`. Running the full suite in parallel let one test's inserted well satisfy the other test's "should be unresolved" assertion, hiding it non-deterministically depending on test-scheduling order. Fixed by picking a value confirmed (via `grep`) not to appear in any other test file — the same category of lesson as KS-03/04's object-ID/checksum collisions, but this time a coincidental value collision rather than an identical literal.

### KS-10: monthly lease production, 1990-present (recorded 2026-09-05)

61. **This task finally implements the batch-insert fix KS-08/KS-09 documented and deliberately left undone.** Real production files are an order of magnitude larger than fields/leases (11,678,706 real rows across all 8 real decade archives, confirmed live) — a per-row `INSERT`/upsert loop would have been impractical, not just slow. Both `parse::kgs_production` (staging) and `materialize::kgs_production` (canonical upsert) use `sqlx::QueryBuilder::push_values` for real multi-row `INSERT`s, batched (1000 rows/statement by default) rather than one round-trip per row. Confirmed live: staging all 8 real files took ~9 minutes total (~21,000 rows/sec); a follow-up task should consider retrofitting this same pattern into KS-08's and KS-09's materializers, whose per-row approach remains genuinely slow at real scale.
62. **A real, second performance bug was found and fixed in this task's own live verification, distinct from the batch-insert one**: the materializer's keyset pagination (`WHERE ingestion_run_id = $1 AND id > $2 ORDER BY id LIMIT N`) was initially backed only by a plain `(ingestion_run_id)` index, which left Postgres scanning and sorting the *entire remaining tail* of a run's rows on every single page — effectively O(n²) over an 11-million-row real run (confirmed: materializing 670K rows took 2+ minutes and was still far from done). Fixed by replacing it with a composite `(ingestion_run_id, id)` index in the still-unshipped migration directly (same "edit before it ships" precedent as KS-04's column rename) — confirmed live afterward: the identical 670,863-row run materialized completely in 51 seconds, a ~36x improvement. Recorded here so the *general* lesson — keyset pagination needs an index on exactly `(filter_column, sort_column)`, not just the filter column — isn't rediscovered from scratch next time this pattern is used.
63. **Streaming, not full-file buffering, is required at this row count.** KS-09's lease importer buffered its whole (98,639-row) file into a `String` before parsing — fine at that size, not fine for a 670K-to-2.4M-row production file (the largest real file here is ~190MB uncompressed). `parse::kgs_production::zip_source::stream_production_csv` reads directly from the ZIP entry's `Read` implementation and calls back into the caller once per batch, so peak memory stays bounded regardless of file size; the caller forwards each batch to the async database-writing task over a `tokio::sync::mpsc` channel from inside `spawn_blocking`, so CSV parsing (CPU-bound, blocking) and database writes (IO-bound, async) overlap instead of serializing.
64. **The pre-1990 legal-review gate is enforced per-row at ingestion time, not just by which files are configured.** `constants::KGS_PRODUCTION_FILES` already excludes anything older than 1990 (decided at KS-003), but the task doc explicitly asks for a *rejectable* runtime guard, not just a curated file list — `constants::is_production_year_ingestible(year, override_enabled)` is checked against every row's own parsed year during staging, and a row failing it is rejected with a specific reason distinct from "unparseable," never silently coerced or silently included. `constants::PRE_1990_LEGAL_REVIEW_OVERRIDE_ENV` is the named, unmistakable env var the task doc's "unless a separate future legal-review feature flag is explicitly enabled" clause requires.
65. **"Do not duplicate month 0 or -1 into monthly charts" is enforced by a structural column (`record_kind`), not a query-time convention someone has to remember.** Every row — monthly, yearly-total, or starting-cumulative — is stored in the same `ks_lease_production_month` table (never dropped), but `record_kind` is derived once via the existing `constants::classify_production_month` (built at KS-003, unused until now) and a partial index (`WHERE record_kind = 'monthly'`) exists specifically so a correct monthly-chart query is also the fast one.
66. **Reconciliation is against KGS's own redundant reporting, not a separate confirmed "official total" feed.** The task doc asks to "reconcile imported totals against KGS state, county and field totals," but no separate state/county/field total dataset is confirmed to exist as its own source — `materialize::kgs_production::reconciliation_report` instead compares the sum of real monthly rows against KGS's own reported yearly-total (`month = 0`) rows for the same group/product/year. A discrepancy here means KGS's own monthly and annual figures disagree with each other, which is exactly the kind of thing worth surfacing; this is an honest, data-grounded interpretation of the requirement, not a claim that an external state-total feed was integrated.
67. **KS-10 completes `constants::ProductionRecordKind`/`classify_production_month`'s round trip**: both were built at KS-003 specifically for this task and sat unused for months of task history — a reminder that "build the fixed shape now, implement the importer later" (the pattern used repeatedly across KS-003's contracts) is a real, working strategy, not just aspirational documentation.
68. **KS-12/KS-13 finally build item 18's `state-export-v1` exporter** (`src/state_export/`), previously tracked only as the internal placeholder number "KS-020." Both tickets explicitly forbid a standalone Kansas map or entity-detail UI and instead require extending the shared Future Wells Co platform — the exporter is the entire Kansas-side surface area those tickets actually need from this repo; `futureBackend` already has a mature multi-state map/clustering/entity-detail API and Kansas was already registered there as a `state-export-v1` data source (`data_sources.source_code = 'kansas_backend'`, `jurisdictions.rollout_stage = 'flagged'`) before this task started. See `docs/ops/ks-12-13-state-export-live-smoke.md` and `docs/ops/ks-12-13-shared-infra-handoff.md`.
69. **Baseline/full exports only — incremental is deliberately not implemented.** `futureBackend`'s own reference exporter (New Mexico's `src/state_export/exporter.rs`, used as the real, working template this module was built against) supports incremental exports via a `state_export_change_log` table and per-source-table triggers. Kansas has no equivalent change-data-capture infrastructure, and the contract explicitly allows a baseline/full export to disable row-level change logging — so `export_state_v1` rejects `ExportModeV1::Incremental` with a clear error rather than faking a partial diff. Every Kansas canonical table already carries a stable internal UUID primary key (KS-04 through KS-10's own discipline), so `state_export::keys` needed none of New Mexico's natural-key synthesis logic — it just wraps that id.
70. **Comments are never exported, in any form.** KS-12 requires raw KGS comments never reach a map popup and only reach a detail view "after sanitization" — since no sanitization step exists anywhere in this repo, `ks_well.comments` is excluded from the export entirely (not even into `source_payload`) rather than shipped unsanitized to a platform this repo doesn't control the rendering of.
71. **A real, concrete gap in the shared contract itself, found only by actually building against it**: `contract::ProductionMonthlyV1` has no lease/regulatory-area foreign key at all — only `well_source_key`/`operator_source_key`. Kansas lease production is lease-level (the contract's own "Unresolved Relationships" section anticipates exactly this: `well_source_key = None`, `relationship_resolution_status = "unresolved"`), but there is nowhere typed to put *which lease* the row belongs to; this export stuffs `lease_kid`/`reported_lease_name`/etc. into `source_payload` as a stopgap. KS-13's lease detail page ("show lease-level monthly production and all linked wells") cannot be fully served by the shared platform until `futureBackend` adds a lease/regulatory-area link to that entity — see the handoff doc.
72. **Field and lease both export as `regulatory_areas`** (`area_type = "field"` / `"lease"`), matching `futureMarketing`'s own generic entity-detail routing (`field|lease|pool|district|formation → regulatory-areas`, confirmed by reading that repo before writing this exporter) — not a Kansas-side workaround, but the shared platform's actual intended extension point for exactly this kind of entity.
73. **KS-14 has no cross-repo dependency**, unlike KS-11/12/13 — event generation and watch-area matching are entirely `kansasBackend`-internal (delivery/notification does not exist and is out of scope; no account system exists to notify). `ks_event`'s new typed relationship columns (item 74) double as what KS-12/13's exporter reads for its own `events` entity, so KS-14 also simplified that exporter code (item 76).
74. **Baseline-event suppression's cutoff is a fixed constant, not an env var, on purpose.** `constants::LIVE_MONITORING_CUTOFF` could have been env-configurable (the pattern KS-10's `PRE_1990_LEGAL_REVIEW_OVERRIDE_ENV` established), but every event-emitting materializer runs inside this repo's shared-database `#[tokio::test]` suite, where an env var is process-global mutable state unsafe to change from a test running concurrently with the rest of the suite. `constants::should_emit_event` takes `cutoff` as an explicit parameter instead, keeping the suppression *decision* fully unit-testable while the constant itself only changes via a code edit.
75. **A real bug that only integration-testing found, not reasoning about the design**: the first `should_emit_event` fell back to `observed_at` when `occurred_at` was `None`. Since `observed_at` during a backfill run is always "now" (whenever the backfill happens to execute), that fallback is always at or after any sane cutoff — it silently defeated suppression for exactly the event type with no source-reported date (`WELL_STATUS_CHANGED`, since neither KGS field carries an exact status-change date). Fixed by dropping the `observed_at` parameter from `should_emit_event` entirely: an unknown `occurred_at` during a backfill now always suppresses. General lesson: a "fall back to processing time" default is rarely safe for a suppression/backfill decision specifically, since processing time is definitionally always recent.
76. **A second real bug, same root cause (letting a per-run mechanical signal drive a decision that must be invariant across reruns)**: `materialize::kgs_production`'s first implementation used the SQL `RETURNING (xmax = 0)` insert flag to decide `FIRST_LEASE_PRODUCTION_REPORTED` vs. `LEASE_PRODUCTION_UPDATED`. A plain re-observation of unchanged data is always an SQL `UPDATE` (the row already exists), which reclassified it as "updated" on the second run — and because `ks_event`'s `(event_type, dedup_key)` uniqueness is scoped *per event_type*, the same dedup-key string under a different event_type is not caught by `ON CONFLICT DO NOTHING`, producing a spurious duplicate notification for a value that never changed. Fixed by resolving "has this exact fact (embedding the actual value) already been reported, under either event type" before ever choosing which type to assign — see the module's own doc comment for the full design. Both this and item 75 were caught by real integration tests (`tests/kgs_wells_materialize.rs`, `tests/kgs_production_materialize.rs`), not found by inspection.
77. **A third real bug, in KS-12/13's own `state_export::exporter::export_events`, exposed by KS-14 rather than introduced by it**: that query joined `ks_drilling_intent` via `e.event_type = 'INTENT_POSTED' AND di.id = e.dedup_key::uuid`. This was never actually safe — Postgres's planner is free to evaluate a hash join keyed on `e.dedup_key::uuid` for every row of `ks_event` before the `event_type` predicate applies at all, regardless of AND-clause ordering in the SQL text — it simply had nothing to crash on until KS-14 introduced event types with non-UUID dedup keys (e.g. `"lease_kid:product:year:month:volume"`). Fixed two ways: `export_events` now reads `ks_event`'s own new typed relationship columns directly (simpler and no longer needs the join at all), and the general lesson — a multi-predicate join condition does not guarantee left-to-right short-circuit evaluation the way a `CASE WHEN` expression does — is recorded here in case a similar pattern is ever needed elsewhere.
78. **`expire_stale_intents`'s necessarily-global scan gave `tests/kcc_intents_materialize.rs` the identical test-isolation hazard `tests/kgs_wells_materialize.rs` already documented at length for well tombstoning**, and for the same underlying reason: correctly modeling "which previously-known intent is missing from this fresh snapshot" requires comparing against every not-yet-expired intent in the database, not a subset scoped to the calling test's own fixtures — confirmed empirically (without `#[serial]`, other tests' intents got expired mid-run, and this file's own target intent was sometimes expired a full run early purely from test interleaving). Fixed the same way: `#[serial]` (listed before `#[tokio::test]`, per the established convention) added to every test in that file.

79. **KS-15 confirms KGS is reachable and structured well enough to build real, live-verified code against — unlike KCC/KOLAR** (`kcc.ks.gov`/`kolar.kcc.ks.gov` both confirmed unreachable again this task). But the real page shape found (KGS's "Qualified Well Database" per-well detail page) does not expose a downloadable document manifest at all — it links to a login-walled library (Walter's Digital Library) and separately cites document existence/dates in a "Tops Data" table. Both `classify_access_state`'s rules (the `kgslibrary.com`/"login required" match, and the `robots.txt`-disallowed path list) are transcribed directly from real, confirmed-live data fetched during this task, not guessed — see `docs/ops/ks-15-kgs-documents-live-smoke.md` for the exact URLs and `robots.txt` excerpt.
80. **No bulk Kansas well-document index exists** — the real per-well detail page is the only confirmed-live document-adjacent endpoint, so `snapshot-documents-for-well` is per-KID by design. A full statewide index would mean ~180,000 fetches (one per Kansas well), the same "known, real, unfixed scaling characteristic" class KS-08/KS-09 already documented for their own per-row materialize throughput (items 49/59) — not executed at that scale in this session.
81. **`ks_well_document`'s `parser_status`/`public_access_state` CHECK constraint (migration `0027`) structurally prevents the "controlled queue" from ever being bypassed** — a document observed as anything other than `public` cannot reach `parser_status = 'queued'` even if application code tried, mirroring this repo's established preference (see e.g. item 61's tombstone-vs-missing-count discipline) for enforcing a hard rule in the schema itself rather than only in the materializer that happens to populate it today.
82. **A real bug KS-15's own tests caught, not inspection**: `extract_tops_data_citations`'s header-column detection used `.contains("source")` to find the "Source" column, which false-matched the same table's own "Formation (source name)" header (column 0) instead of the real "Source" column (column 3) — both literally contain the substring "source." Fixed with exact post-trim string equality. A second instance of the same general lesson items 75/76 already recorded this session: a "contains" heuristic is rarely safe when a table's OWN column names can legitimately contain the search term as a substring of an unrelated label.

83. **KS-16 is a research spike that shipped zero production code, by design** — `docs/research/ks-16-horizontal-trajectory/` holds the entire deliverable (sample manifest, format fixtures, taxonomy, recommendation). No migration, no `src/` changes. The one artifact that touches previously-shipped work is an addendum appended to `docs/ops/ks-15-kgs-documents-live-smoke.md` (not a rewrite of it) recording that KS-16 found real, unauthenticated, robots-compliant document access for wells filed since roughly the early 2010s — a materially different finding than KS-15's own single 1980-vintage sample implied, but not a contradiction (different document vintages).
84. **KS-16's real sample directly demonstrates why "index metadata now, download later" (KS-15's own design) was the right call**, not just a cautious default: even among real, digitally-filed horizontal wells, one of three deep-sampled documents turned out to carry no usable trajectory data at all (a 1928 scan misclassified by KGS's own "horizontal wells" query), and the one genuinely rich structured sample found still had no stated datum/projection and real page-wrap artifacts partway through. A production importer built without this research would have had no way to know any of that in advance.

85. **KS-17 has no cross-repo dependency**, same reasoning as KS-14 (item 73) — every check it computes reads only this repo's own tables. What the deferred internal panel/public page need from this module is catalogued in `docs/ops/ks-17-monitoring-handoff.md` rather than built here.
86. **A "fact table vs. dimension table" reporting bug, a generalizable lesson distinct from anything caught earlier this session**: `row_count_change_report`/`schema_fingerprint_change_report`/`content_type_change_report` were each first written `FROM ks_ingestion_run JOIN ks_source` — starting from the table that only has a row when something actually happened. A source with zero completed runs ever therefore never appeared in the report at all, rather than appearing with `None` fields — exactly backwards for a monitoring module whose entire purpose is to surface "this source has no data," not omit it. Fixed by starting every one of these three queries `FROM ks_source LEFT JOIN ks_ingestion_run` instead — the dimension table drives the report, the fact table only fills it in when present. Caught by a real test failure (`schema_fingerprint_change_is_none_when_unknown_and_some_when_known`, run against `KCC_CONSERVATION_DOCKETS`, a source with genuinely zero import history since no importer for it exists yet), not by inspection.
87. **A second real bug, found while writing this module's own handoff documentation, not by a test**: `staleness_threshold_hours` matched `ks_source.expected_cadence` by exact string equality against `"nightly"`/`"daily"`/`"weekly"`/`"monthly"`. But the real seeded cadence values (migration `0002`) include `daily_rolling_365`, `daily_rolling_90` (KCC's rolling-window sources), and `continuous` (`KCC_OPERATORS`) — none of which equal the literal string `"daily"`. Three real sources with a genuine, documented cadence therefore silently fell through to `None` (no threshold at all) and could never be reported stale no matter how far out of date they became — the opposite failure mode of item 86, but the same root cause: a check written against an idealized/simplified view of the data (assuming cadence values are always one of four fixed words) rather than the real, already-seeded values. Fixed by matching on prefix (`starts_with("daily")`/`starts_with("nightly")`/`starts_with("monthly")`/`starts_with("weekly")`) plus an explicit `"continuous"` case, with a new pure unit test enumerating every value actually seeded in `ks_source` today so a future new cadence string added there without a matching code change would be caught immediately rather than silently falling through again.
