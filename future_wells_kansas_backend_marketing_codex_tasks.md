## 1. Research conclusion

Kansas is attractive because the Kansas Geological Survey (KGS) provides a strong statewide well and production foundation, while the Kansas Corporation Commission (KCC) supplies the more time-sensitive regulatory signals. Unlike most sibling states (a single WOGCC/OCC-style commission), Kansas splits this across two agencies with different cadences, different legal-use restrictions, and no shared identifier scheme — the architecture must treat them as two first-class source families, not one.

## 3. Kansas-specific modeling decisions

These decisions bind every table design in §6 (canonical data contracts). Where noted, they are already implemented as tested code (KS-003), not left as prose for a later task to remember.

### 3.1 API number is canonical; KGS KID is an alias

Use the normalized Kansas API number as the preferred external well identity whenever one is present. Store both the dashed source value and the normalized digit-only API-14.

KGS explicitly states its KID is not necessarily permanent — it must live in a source-alias table, never serve as the permanent Future Wells well primary key. The same caution applies to `LEASE_KID`.

```
internal_well_id           UUID
state_code                 KS
api_raw                    15-009-22036-0001
api14                      15009220360001
kgs_kid                    source alias
kcc_permit                 source alias
source_identity_confidence exact | probable | unresolved
```

`source_identity_confidence` is `constants::SourceIdentityConfidence` (done, KS-003) — every identity-resolution step (KS-005+) must set it explicitly rather than defaulting silently to `exact`.

### 3.2 Operator information is versioned, never overwritten

KGS's well file carries an original operator and a reported-current operator, but KGS itself warns the reported-current value is not guaranteed to be the actual current operator. KCC operator licenses and approved-transfer records are separate evidence streams, not confirmation of KGS's field.

Never overwrite an operator relationship solely because a fuzzy lease-name match suggests a transfer — every relationship is an appended row, never a field overwrite:

```
operator_relationship
valid_from
valid_to
source
match_method
confidence
is_current_reported
```

Materializes as `ks_well_operator_history` (§6.1b) — closed by setting `valid_to` on supersession, never `UPDATE`d over. This refines the source-authority rule in §4 item 4: KCC evidence sets `is_current_reported = true` on the winning row; KGS's own original/reported-current fields are retained on `ks_well` as separate, clearly-labeled raw evidence, never silently overwritten by the KCC-derived history.

### 3.3 Preserve source coordinates; transform for display

KGS describes location fields as NAD27, frequently generated from legal-location (PLSS) information, with some newer GPS-sourced locations. Store the source values and a derived WGS84 display geometry side by side — the transform is additive, never a replacement of the source values.

```
source_latitude
source_longitude
source_crs
display_geometry_4326
location_source
location_confidence
location_warning
```

For the ArcGIS adapter (KS-005), request `outSR=4326` and still retain the raw source latitude/longitude columns for provenance.

### 3.4 Production must remain lease-level

Do not allocate a lease's production evenly across its linked wells. Do not label lease totals as "well production." Kansas production records can list one or more linked API numbers and a contributing-well count, but KGS describes that count as limited quality — it is context, not a division key.

Marketing copy (KS-M005) must say:

> **Linked lease production.** Production is reported for the lease and may include multiple wells.

Oil units are barrels; gas units are MCF. Month `0` represents yearly totals and month `-1` represents starting cumulative values — both are real KGS record kinds, not malformed data, and must never be mixed into the monthly series. `constants::ProductionRecordKind` and `constants::classify_production_month` (done, KS-003) classify a raw month value into `Monthly | YearlyTotal | StartingCumulative` (or `None` for anything else, which must be treated as a parse failure, not silently dropped) so every downstream query can filter to real months explicitly.

### 3.5 Build lifecycle from multiple raw fields

The KGS ArcGIS layer separates well type/status concepts across `WELL_CLASS`, `STATUS`, and `STATUS2`. Its coded values include oil, gas, injection, saltwater disposal, intent, dry-and-abandoned, and plugged variants. `STATUS=OIL` alone does not mean currently producing.

Preserve all raw status fields and derive one shared Future Wells lifecycle value:

```
planned · intent_expired · drilled · completed · producing · inactive ·
injection · saltwater_disposal · plugged · dry_and_abandoned · unknown
```

`constants::WellLifecycleStatus` (done, KS-003) fixes this enum's shape. The real `WELL_CLASS`/`STATUS`/`STATUS2` coded-value mapping is confirmed and implemented at KS-005 once the file-format doc is parsed. `Unknown` is not a synonym for `Inactive` — an unmapped raw combination must remain visible in a QA report (a `ks_ingest lifecycle-qa-report` command, added at KS-005, listing distinct unmapped `(well_class, status, status2)` triples) rather than silently collapsing to a specific status. Raw fields are always preserved on the well row regardless of how lifecycle_status resolves.

### 3.6 Horizontal wells: badge first, geometry later

The statewide KGS GIS layer is point geometry. KGS separately identifies horizontal or slant wells using a directional indicator in the API, currently around 1,180 records statewide. Public ACO-1 instructions say Mississippi-formation horizontal-well submissions include a directional survey and an as-drilled plat, which makes document-derived lines plausible eventually — but that is not confirmed as a statewide capability today.

For launch:

```
horizontal_or_directional = true    (when the directional indicator is set)
trajectory_available      = false   (unconditionally, for every well)
```

Never draw a guessed lateral from a surface point. `trajectory_available` only becomes `true` once a real document- or survey-derived line exists for that specific well.

### 3.7 Hard data-use controls (enforced in code, KS-003, done)

1. **Block pre-1987 production republication.** KGS licenses pre-1987 production from IHS; it may not be repackaged, resold, or disseminated. `constants::MIN_PRODUCTION_YEAR = 1990` and `constants::is_production_year_ingestible()` encode the MVP boundary of 1990-present only; `constants::KGS_PRODUCTION_FILES` already lists only 1990-present archives, and the test `constants::tests::production_files_never_predate_min_year` fails the build if a pre-1990 archive is ever added without revisiting this guard.
2. **Exclude personal/contact fields from product search and exports.** KCC's intent and operator pages carry a statutory commercial-solicitation certification concerning names and addresses. `src/privacy.rs::assert_no_forbidden_fields` walks a serialized API response for forbidden contact/address field names at any nesting depth and is proven against both a clean and a leaky struct today (`privacy::tests`). Every public-facing operator/intent/transfer response type's own test suite must call it, starting with KS-006 (operators), KS-007 (drilling intents), and KS-008 (transfers).

### 3.8 Keep raw values and source lineage even when normalized values exist

Every normalized/derived field in §6 (`api14` from `api_raw`, `lifecycle_status` from the raw `WELL_CLASS`/`STATUS`/`STATUS2` triple, `display_geometry_4326` from `source_latitude`/`source_longitude`, `record_kind` from the raw `month` value) keeps its raw input sitting right next to it in the same row — normalization is additive, never destructive, matching every pattern already fixed in §3.1-§3.6.

This also binds the KS-020 export: `futureBackend`'s canonical schema (the actual downstream consumer of every state's data) keeps a `source_payload jsonb` column carrying the complete raw record and a `source_payload_hash` for change detection, linked to a specific `import_runs` row for full audit lineage (§10.5). Kansas's `state-export-v1` package must populate `SourceEnvelopeV1.source_payload` with the complete raw source record for every entity, not just the normalized fields that happen to map onto `WellV1`/etc. — a lossy export defeats the lineage guarantee `futureBackend` is built to provide.

### 3.9 Classify Kansas membership before treating any record as a Kansas well (added KS-03)

KGS's own well-master description notes "some data from other states is included for research purposes." Every raw record must be classified before it is treated as a Kansas well, per one of two rules: (1) a valid Kansas API state prefix (`15`), OR (2) WGS84 geometry inside the Kansas boundary AND a valid Kansas county.

Implemented as `constants::{point_in_kansas_bounding_box, is_valid_kansas_county, KS_COUNTIES}` (all 105 real county names) plus `parse::kgs_wells::classify_kansas_membership`. "Inside the Kansas boundary" is implemented as a bounding box, not a precise state polygon — a deliberate scope decision (documented on `KS_BOUNDING_BOX_MIN_LATITUDE` in `constants.rs`): Kansas has no significant irregular border segment that a rectangle would misclassify at meaningful volume against a neighboring state, and pairing it with the county-name check keeps the false-positive rate low without bundling a real polygon shapefile dependency. Revisit with a real polygon only if false positives near the border turn out to matter in practice.

Records failing both rules are **retained**, not deleted, in `ks_well_raw_snapshot` with `kansas_membership_status = 'excluded_other_state'` and a specific reason — raw-first ingestion (§5) applies to excluded records exactly as it does to included ones.

## 4. Source authority hierarchy

1. **KGS is authoritative for well identity and location.** API number, KGS KID, legal location (PLSS), and field assignment come from the KGS well master, not derived or re-geocoded elsewhere.
2. **KCC is authoritative for regulatory/operator status.** Current operator of record, active drilling intents, and approved transfers come from KCC, not inferred from KGS's operator field (which may lag). Materializes as `is_current_reported = true` in `ks_well_operator_history` (§3.2), never as an overwrite of KGS's own reported field.
3. **KGS is authoritative for production, at lease granularity.** Do not attempt to re-derive well-level production from lease-level KGS data by even splitting — report it as lease production and be explicit in the UI that it's lease-level, not well-level, per §3.4.
4. **When KGS and KCC disagree on operator name for the same well/lease**, KCC wins for `is_current_reported`; KGS's own original/reported-current operator fields are retained as separate, clearly-labeled raw evidence, never silently overwritten.
5. **Documents are metadata-first from both agencies**; neither is "more authoritative" for documents — a document catalogued from either source keeps its own source attribution.

## 5. Fixed architecture decisions

See `docs/architecture/kansas-source-boundary.md` for the full list. Summary:

- `{data, meta}` response envelope on every successful API response, matching sibling-state convention.
- Raw-first ingestion: every parser writes an immutable raw-row table before any normalization/materialization.
- Daily-snapshot requirement for both rolling-window KCC sources (drilling intents, approved transfers) — history lives in Kansas's own tables, never assumed still queryable from the source.
- No commercial-solicitation surface: never expose or index KCC operator contact/address/phone data — enforced by `privacy::assert_no_forbidden_fields` (§3.7).
- Metadata-first documents; never bypass a confidential/restricted marker.
- KCC-Connect (not legacy eStar) for any conservation-docket work touching post-November-2025 filings.
- Advisory-lock guard on every ingestion command that writes.
- `clap`-based CLI (`ks_ingest`).
- Bootstrapped from a clean template, not forked from a sibling state repo.
- Identity, operator-versioning, coordinate-preservation, production-discipline, lifecycle-derivation, and horizontal-badge-only rules from §3, several already enforced in code (§3.7).
- No Kansas-specific admin/auth system (no `users`/`sessions`/argon2 login, no `admin_auth` migration). Colorado and Wyoming each independently built one for internal ingestion review and now carry two duplicate implementations of the same thing; `futureBackend` already provides this generically (`AuthenticatedAdmin` + `routes/admin_import_status.rs`, keyed by jurisdiction). Kansas's own ops review goes through that once KS-020 registers Kansas as a jurisdiction — see §10.
- Every task from KS-004 onward ships as one focused PR carrying tests, fixtures (real sample source data, not synthesized), migration notes, rollback notes, and an operational runbook update (`docs/ops/*.md`) — see §10.

## 6. Canonical data contracts (summary — full DDL lands with each task)

Each subsection below is materialized by the backend task noted. Field lists are indicative, not final; the task that materializes a table is where the DDL is authored and becomes authoritative. Enum-shaped fields marked "(constants)" already exist as Rust types (KS-003) that the eventual DDL/materializer must reuse rather than re-deriving.

### 6.1 `ks_well` (done, KS-04)
Canonical well header, one row per resolved well identity, with snapshot history — built by `materialize::kgs_wells::materialize_wells_from_run` (migration `0005_ks_well.sql`). Reads only `ks_well_raw_snapshot` rows belonging to a `completed` `ks_ingestion_run` (KS-03) — a `failed`/`rejected` run's staged rows are never read, enforced by the function itself, not just documented. Identity fields per §3.1, implemented exactly as specified: `internal_well_id` (UUID, PK), `state_code`, `api_raw`, `api14`, `api_base`, `api_suffix`, `api_validation_status` (`valid` | `valid_short_form` | `malformed` | `missing`), `well_identity_match_method` (`api14` | `kid_fallback`) — see `normalize::kgs_wells::parse_api_number`. Descriptive fields: `field_name`, `lease_name`, `well_name`, `operator_name_kgs_original`, `operator_name_kgs_reported_current` (both raw KGS evidence, never overwritten by KCC-derived history — §3.2), `county`, `township`/`township_direction`/`range`/`range_direction`/`section`, `subdivision_1_largest`..`subdivision_4_smallest` + `spot`/`feet_north_from_reference`/`feet_east_from_reference`/`reference_corner` (quarter calls and footages), `permit_date`/`spud_date`/`completion_date`/`plug_date` (parsed) each paired with its own `*_raw` text column, `total_depth`, `producing_formation`, `formation_at_total_depth`, `ip_oil`/`ip_gas`/`ip_water`, `oil_kid`/`oil_dor_id`/`gas_kid`/`gas_dor_id`, `comments`. Location fields per §3.3: `source_latitude`, `source_longitude`, `source_crs` (`'NAD27'`, confirmed authoritative at KS-04 from `kgs.ku.edu/PRS/file_format.html`), `display_geometry_4326` (real PostGIS `geometry(Point,4326)`, built only from `'arcgis'`-sourced rows since only those were actually reprojected via `outSR=4326` — `'zip'`-sourced rows keep NAD27 coordinates with a `location_warning` and no display geometry, pending a real datum transform), `location_source`, `location_confidence` (`gps` | `derived_from_legal_description` | `unknown`, derived only from what KGS's own documentation states). Lifecycle fields per §3.5: `well_class_raw`, `status_raw`, `status2_raw`, `lifecycle_status` (constants: `WellLifecycleStatus`, via `normalize::kgs_wells::derive_lifecycle_status`). Horizontal fields per §3.6: `horizontal_or_directional`, `trajectory_available` — both hardcoded `false` for every row at KS-04, since the "directional indicator in the API" §3.6 refers to was never confirmed against real data (an open item, not a guess dressed up as a finding). ## 8. Marketing architecture

**`kansasMarketing` is a regional SEO/lead-gen content site, not a data-product application.** It carries no well search, no map, and no browse-first navigation (paginated/filterable directories of wells, operators, counties, or fields) — see §10 for why this is a deliberate correction, not the original plan. It publishes editorial content (state overview, guides, coverage/methodology, county-level narrative pages) and converts visitors into the one real cross-state product, `futurewells.co`'s `user-area`, via the shared `RecordConversionCta` component (ported from `coloradoMarketing`/`wyomingMarketing`, done at KS-M001) and direct links to `config/userArea.ts::futureWellsUserAreaRegisterUrl`.

Next.js 14 App Router, `site-config.mjs` as the single per-state identity file, `app/kansas/...` for all public content per the `/<state>/...` route convention. If a `lib/api/*` client is ever added (KS-M002, only if a content page needs a live coverage/freshness fact from the backend), it stays server-side only, hitting `BACKEND_API_URL` — the browser must never call `kansasBackend` directly, since there is no public data-browse surface for it to power.

`site-config.mjs` sets `stateCode: "KS"`, `stateSlug: "kansas"`, `defaultSiteUrl: "https://futurewellskansas.com"`, `officialAgencyName: "Kansas Corporation Commission"` (primary regulator) with KGS credited separately wherever production/well-master data is shown, since the two agencies are legally distinct data owners (§1). `features.operators`/`features.counties`/`features.wellOverview`/`features.production`/`features.maps` are all `false` — they gated the now-out-of-scope directory/search/map pages and are kept as an explicit off-switch rather than deleted, so a future decision to add them back is a one-line flip, not a rediscovery.

## 10. Shared-platform architecture correction (recorded 2026-09-05)

Before KS-004 started, an explicit instruction arrived to treat Colorado's implementation and the shared cross-state platform as the reference architecture rather than continuing to mirror Wyoming. A full read-only investigation of `coloradoBackend`, `coloradoMarketing`, `futureBackend`, and `futureMarketing` was run first, per that instruction's own "before changing code" gate. This section records what was found and the resulting binding decisions — later tasks should treat this as settled, not re-litigate it, unless new evidence turns up.

### 10.1 What actually exists

- **`futureBackend` is the real multi-state system**, not any per-state repo. Its schema is parameterized by `jurisdictions` (`country_code`/`state_code`/`state_name`) and `data_sources` (`jurisdiction_id`/`source_code`/`supported_schema_version`); one `wells`/`operators`/`counties`/etc. table set serves every state, keyed by `jurisdiction_id` + `data_source_id` + `source_key`. Per-state onboarding is a small seed migration (`colorado_state_import_source.sql`, `wyoming_state_import_source.sql`, etc.).
- **Every per-state backend (Colorado, Wyoming, ND, OK, NM) is single-state**, structurally like `kansasBackend` already is — its own DB, own ingestion, own read API — and *feeds* `futureBackend` via a `state-export-v1` JSON export. This part of the existing Kansas plan (§4-§9) needed no structural change: Kansas correctly stays a standalone ingestion+read backend.
- **There is one real customer account system: `futureBackend`**, surfaced at `futurewells.co/user-area/*` (search, wells, map, entities, production, saved records, billing). Neither `coloradoMarketing` nor `wyomingMarketing` has its own customer signup — both funnel visitors to `futurewells.co/user-area/register` via a `RecordConversionCta` component, byte-identical between the two repos.
- **Colorado and Wyoming each separately built their own *internal/admin* auth** (`users`/`sessions` tables, argon2, a `future_wells_session` cookie, login/logout/me/admin-recent-activity) purely for staff ingestion review — the same thing implemented twice, independently. `futureBackend` already has a generic equivalent for this exact job (`AuthenticatedAdmin` + `routes/admin_import_status.rs`, keyed by jurisdiction, rendered at `futureMarketing/app/superadmin/imports/page.tsx`). This is the "duplicate account system" the correction warns against — Kansas was not yet guilty of it (no admin/auth task had been queued), and §5/§7 now say explicitly not to build one.
- **`coloradoMarketing` currently *does* have a large public well search/map/browse surface** (`/colorado/wells`, `/map`, `/colorado/{counties,operators,fields}`, production rankings, activity feed) — this contradicts a first-pass reading of "match Colorado" literally. The working interpretation, stated explicitly here rather than left implicit: that surface is legacy/technical debt that predates (or duplicates) the shared `user-area` product, not the target to replicate further. The explicit instruction ("no public search, map, or browse-first navigation on the Kansas regional marketing site") is followed as written regardless of what Colorado currently has; Kansas is not to become a third independent implementation of the same self-hosted browse layer. **This interpretation is not confirmed by any design doc in either repo — flagged here in case it needs correcting.**
- **"Shared components/ingestion envelopes/source attribution/events/map layers/entity models"** are, with one exception, a *pattern* to replicate per-state, not a real shared package — confirmed by three near-byte-identical copies of `state_export/contract.rs` across ND/OK/NM differing only in a `SOURCE_CODE` constant, and Colorado implementing the same wire format in Python instead of Rust. The one real shared artifact is the **wire format itself**, canonically typed in `futureBackend/src/imports/contracts/v1/mod.rs` (`StateExportManifestV1`, `SourceEnvelopeV1`, `WellV1`, `OperatorV1`, `RegulatoryRecordV1`, `EventV1`, `ProductionMonthlyV1`, etc.) — this is what KS-020 must target precisely. "Events" has two unrelated senses in that codebase: ingestion-run provenance (`import_runs`/`import_batches`/etc.) and regulatory/docket activity (`EventV1` → `regulatory_events`, which is what a future Kansas docket export feeds) — don't conflate them. No `SourceAttribution` component exists in Colorado at all (the one in `wyomingMarketing` was purpose-built there); no shared map-layer module exists either.

### 10.2 Binding decisions for Kansas

1. `kansasBackend` remains its own standalone repo (ingestion + read API + `ks_ingest` CLI) — this was already correct.
2. `kansasBackend` never builds its own admin/auth/`users`/`sessions` system. Ops review of Kansas ingestion goes through `futureBackend`'s existing `AuthenticatedAdmin`/`admin_import_status` once KS-020 registers Kansas as a jurisdiction.
3. `kansasMarketing` never builds public well search, a public map, or browse-first (paginated/filterable) directories of any entity. Its public surface is editorial SEO/lead-gen content that converts to `futurewells.co/user-area` via the ported `RecordConversionCta` — done at KS-M001 (`components/future/RecordConversionCta.tsx`, `config/userArea.ts`, `app/analytics.ts`, wired into the `/kansas` landing page).
4. KS-020 (`state-export-v1` export) is promoted from "optional" to load-bearing: it is the only path by which Kansas wells ever reach a real search/map/save experience, since `kansasMarketing` deliberately never builds one itself.
5. Raw values are kept alongside normalized ones at every layer, culminating in a fully-populated `SourceEnvelopeV1.source_payload` at export time (§3.8) so `futureBackend`'s `source_payload`/`source_payload_hash`/`import_runs` lineage chain is never lossy for Kansas data.
6. Every task from KS-004 onward ships as one focused PR: tests, real fixtures (not synthesized), migration notes (what changed and how it rolls forward), rollback notes (how to undo it), and an operational runbook update under `docs/ops/`. This is a delivery-process rule, not a one-time task, and applies for the life of the project.
